# Debugger Workflow

## What is and is not available

The instrumented Gens build this project uses
([gens_automation](https://github.com/oranguthang/gens_automation)) has no
symbol-file loader. There is no way to point it at a symbol table and get named
labels in its disassembly window, and this document does not pretend otherwise.

What it does have is a Lua interpreter, frame-ranged CPU tracing, binary memory
and DMA tracing, and full emulator state dumps. Those work on addresses, so the
useful thing the source can contribute is an accurate address-to-name map plus
the tooling to apply it after the fact.

```bash
make symbols
```

produces two files:

| File | Contents |
| --- | --- |
| `build/flicky.sym` | `ADDRESS NAME`, one per line, sorted by address |
| `build/debug_symbols.json` | Resolved breakpoints and watches, plus counts |

`flicky.sym` is the plain format most Mega Drive debuggers accept, so a
different emulator -- BlastEm, Exodus, the Mesen fork -- can load it directly
even though Gens cannot.

## Where the symbols come from

From the assembler listing, not from the assembler's symbol table. AS emits a
symbol table but uppercases every name, which would destroy the casing that
`docs/naming.md` depends on: `Player_CheckGround` and `PLAYER_CHECKGROUND` are
not equally useful. `scripts/debug_symbols.py` parses the listing rows instead,
where each line carries the address it assembled at next to the original source
text.

The listing is a build artifact. It is regenerated by `make flicky.lst` and is
never tracked.

## Breakpoints and watches

`config/debugger_breakpoints.json` and `config/debugger_watches.json` name
symbols, never addresses. `make symbols` resolves them and fails if any name no
longer exists, so a rename that breaks a debugging aid is caught at build time
rather than the next time somebody tries to use it.

The breakpoints cover the frame loop and mode dispatch, the object system, the
player, scoring, level construction, sound and decompression -- the places where
a session usually starts. The watches cover frame and mode state, progress,
gameplay counters, camera position, the two difficulty speeds and the sound
command bytes.

## A session

1. `make verify` first. Debugging a build that does not match the reference
   wastes the session.
2. `make symbols` to refresh the map.
3. Look up what you want in `build/flicky.sym`:

   ```bash
   grep Player_CheckGround build/flicky.sym
   ```

4. Run the emulator with the movie and a frame-ranged CPU trace around the
   frame of interest, taken from the scene index in `movies/`:

   ```bash
   "$GENS_EXE" -rom fbuilt.bin -play movies/flicky_longplay.gmv \
       -trace-start 700 -trace-end 760 -turbo -nosound
   ```

5. Cross-reference the addresses in the trace against `flicky.sym`.

For state rather than control flow, `-save-state-dumps` writes a `.genstate`
per capture containing work RAM, VRAM, CRAM, VSRAM, the VDP registers, Z80 RAM
and the sound chip state. The RAM section can be read directly against
[`ram_fields.md`](ram_fields.md).

## The stubbing technique

The fastest way to find what a routine does is still to remove it. Replace its
first instruction with `rts`, rebuild, and replay the movie against a reference
capture; `make analyze` automates exactly that across many routines in
parallel. It answers "what breaks without this" without needing a debugger at
all, which is how most of the naming in this reconstruction was established.

Remember to `make verify` afterwards: a stubbed build is deliberately not
byte-identical, and leaving one in the working tree is how a real change gets
lost.
